## 4. Behavior Wiring

### Single-node vs multi-node

This is decided by **`WorkflowKind`** and the constructed task graph, not by `SessionMode`. The wiring lives in `packages/engine/src/domain/workflow.ts`:

- **`createSingleTaskWorkflow()`** — `workflow.ts:72–86` — builds `kind: "single-task"`, exactly one task, `policy.maxConcurrent = 1`.
- **`createThinkThreadWorkflow()`** — `workflow.ts:88–102` — `kind: "think-thread"`, one task, `policy.maxConcurrent = 1`. Note `mergeTarget` is `Omit`'d from the spec — think threads do not merge.
- **Multi-node DAG** — generated by the planner (`packages/engine/src/application/planner-service.ts`). `VALID_KINDS` at `planner-service.ts:6` is `{"single-task", "manual-dag"}`; the system prompt at `:20–38` instructs the LLM to emit `"manual-dag"` when the work has ordered sub-steps, otherwise `"single-task"`.
- **Workflow validation** — `createWorkflow()` at `workflow.ts:9–70` enforces `kind ∈ WORKFLOW_KINDS`, ≥1 task, unique IDs, valid dependsOn, and acyclic graph (`assertAcyclic()` at `workflow.ts:132–`).
- **Default concurrency** — `workflow.ts:57` sets `maxConcurrent: spec.policy?.maxConcurrent ?? 3` for generic DAGs.

The UI surfaces this distinction via the `KindPill` helper at **`packages/web/src/views/list.tsx:265–`**: `single-task` is shown as "task", `think-thread` is shown as "think". The list filter at `list.tsx:18` (`FilterMode = "all" | "task" | "dag-task"`) groups `single-task` and `think-thread` under "task" (`list.tsx:107–108`).

### Read-only vs write-capable

There is **no per-mode read-only flag**. Read/write control is per-task via `Claim`s, and there's a separate session-level `permissionTier`:

- **`Claim.mode`** — `packages/engine/src/domain/types.ts:42` — `"read" | "write"`. Claims are stored on `TaskNode.claims` (`types.ts:87`) and copied from `TaskSpec.claims` in `createTaskNode()` at `workflow.ts:114`.
- **Conflict detection** — `packages/engine/src/domain/claims.ts` — `findClaimConflicts()` skips read/read pairs and reports overlaps otherwise. Used by the scheduler at **`packages/engine/src/application/scheduler.ts:57`**:
  ```ts
  return findClaimConflicts(task.claims, holder.claims).length === 0;
  ```
  This is what gates concurrent execution of write-mode tasks against overlapping paths.
- **`PermissionTier`** — `packages/shared/src/session.ts:30–31` declares `"read" | "worktree" | "full"` and `Session.permissionTier` at `:99` carries it. Grep shows this symbol is declared but no other file currently consumes it (search across `packages/`: only `session.ts` matches). It is a declared session-level capability tier that is not yet wired into UI selection or runtime enforcement here.

### Mode → Workflow shape mapping

The two namespaces (`SessionMode` and `WorkflowKind`) overlap but are not the same:

- `SessionMode = "task"` ↔ usually `WorkflowKind = "single-task"` (single-node).
- `SessionMode = "think"` ↔ `WorkflowKind = "think-thread"` (single-node, no merge target).
- `SessionMode = "dag-task"` / planner-built workflows ↔ `WorkflowKind = "manual-dag"` (multi-node).
- `SessionMode = "ship"` ↔ `WorkflowKind = "ship"` (multi-stage; `ShipStage` at `session.ts:28` enumerates `"think" | "plan" | "dag" | "verify" | "done"`).
- `SessionMode = "loop"` ↔ `WorkflowKind = "loop"`.

The `NewSessionView` only emits `single-task` or planner-built (`single-task`/`manual-dag`) workflows. The other modes are entered via slash commands or engine-side spawners.
